# 複数店舗 × 複数LINEアカウント運用と統合分析

このドキュメントは、複数店舗のレシート画像運用を想定し、  
「店舗ごとにLINE公式アカウントを分けつつ、売上データは1つのDBで統合管理する」方針を説明します。

## 結論

- 店舗ごとに別LINEアカウント（別チャネル）を使う運用は可能
- 受信経路は分かれても、DBは1つに統合できる
- 統合後に、店舗比較・全店合計・ランキングなどの分析が可能

## 背景（なぜ分けるか）

- LINEの送信上限（プラン上限）はアカウント単位で管理される
- 1アカウントに全店舗を集約すると上限消費が早くなる
- 店舗単位でアカウントを分けると、送信枠を分散できる

## 推奨アーキテクチャ

1. 店舗ごとにLINE公式アカウント（チャネル）を発行  
2. 各チャネルのWebhookを同一システム（Supabase Functions）で受信  
3. 受信時にチャネル情報を解決し、同一DBへ保存  
4. `store_id` を軸に集計し、管理画面で比較・統合表示

## データ設計（最低限必要な項目）

レシート行データに、以下を必須で保持します。

- `store_id`: 店舗識別子（分析の主キー）
- `channel_id`: どのLINEチャネル経由か
- `receipt_date`: レシート日付（JST基準で欠損させない）
- `gross_sales_yen`: 総売上
- `party_count`: 会計組数
- `guest_count`: 客数

任意であると便利な項目:

- `brand_id`
- `area`
- `business_type`

## 分析でできること

- 店舗別売上の比較（今月、前年同月、曜日別）
- 全店合計の可視化（売上、客数、客単価）
- 店舗ランキング（売上・成長率・客単価）
- グループ別比較（ブランド別、エリア別、業態別）
- 異常検知（特定店舗の急落・急増）

## 実装時の注意点

- 店舗名ではなく `store_id` で統一管理する（表記ゆれ対策）
- `receipt_date` の欠損を防ぐ（欠損は集計ズレの原因）
- タイムゾーンをJSTで統一する
- webhook受信と返信ログに `store_id` / `channel_id` を残す

## 運用上の留意点

- 複数LINEアカウント運用は管理コストが上がる
  - 友だち追加導線
  - 問い合わせ先の分散
  - 店舗ごとの認証情報管理
- そのため、導入前に以下を決める
  - アカウント命名規則
  - 権限管理ルール
  - 障害時の運用手順

## 段階的導入の提案

1. まず1〜2店舗で試験運用  
2. データ品質（`receipt_date` 欠損、店舗識別）を確認  
3. 管理画面で店舗比較の表示を整備  
4. 問題なければ全店舗へ展開

## まとめ

- 店舗ごとにLINEアカウントを分けても、データ統合分析は可能
- 重要なのは、受信経路ではなくDB側の識別キー設計（`store_id`）
- 正しく設計すれば、全店統合と店舗別比較を同時に実現できる
